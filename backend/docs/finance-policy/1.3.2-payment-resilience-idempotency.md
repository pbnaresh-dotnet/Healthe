# Finance Policy v1.3.2 — Payment Resilience & Idempotency

**Effective:** 2026-10-08  
**Source reference:** `FIN-Phase-2E-PAYMENT-RESILIENCE-IDEMPOTENCY`

Payment creation is idempotent at the application and provider boundary. A customer request supplies an idempotency key. The system stores a deterministic request fingerprint and rejects reuse of that key for a materially different payment request.

If the application loses connectivity after the provider accepts an order but before the local payment row is updated, a retry reuses the existing payment transaction, provider order ID and idempotency key. It must not create a second provider order.

Transient Cashfree failures are retried with a bounded exponential backoff. Provider Retry-After is honored when supplied, and retries are capped. Non-transient failures are not blindly retried.

Payment completion is state guarded. Once a payment is verified as Paid, stale or non-success status responses cannot downgrade it. Duplicate webhook delivery may therefore safely re-enter the verification/completion path without creating duplicate fulfilment.

Operational retry state—attempt count, last attempt, next retry, processing status and last error code—is retained on the payment transaction.
