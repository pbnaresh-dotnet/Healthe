# Finance Policy v1.3.6 — Durable Payment Retry & Idempotent Provider Recovery

**Effective:** 2026-10-08 UTC  
**Source code reference:** `FIN-Phase-2F-DURABLE-PAYMENT-RETRY`

## Purpose

Define how failed payment-provider order creation is recovered without creating duplicate provider orders, duplicate charges, or duplicate financial records.

## Rules

1. A provider-order creation failure remains a `Pending` payment transaction with `ProcessingStatus = ProviderOrderCreationFailed`, an incremented attempt count, last-attempt timestamp, bounded next-retry timestamp and error code.
2. Only `CustomerSubscription` payments in the retryable provider-order state are automatically recovered by the worker. Outlet-onboarding payment creation retains its existing explicit onboarding flow and is not silently reinterpreted by the customer retry worker.
3. Retry eligibility requires the persisted `NextRetryAtUtc` to have elapsed and `AttemptCount` to remain below the configured maximum.
4. Retry candidates are atomically claimed in the database before provider communication. This prevents multiple application instances from concurrently retrying the same payment.
5. A retry reuses the original provider order ID and original idempotency key. A retry must never create a new logical payment request.
6. Cashfree transport retries remain bounded and use the same idempotency key for transient HTTP failures.
7. Successful provider-order creation clears the retry schedule and records the provider checkout session/status.
8. A failed retry persists the next bounded retry time and failure details. No financial document, revenue, tax or settlement record is created merely because a retry was attempted.
9. The retry worker uses configurable polling interval, maximum attempts and batch size. Defaults are 15 seconds, 6 attempts and 20 records per batch.
10. At maximum attempts, the payment remains `Pending` with its final failure evidence and is not retried automatically until an explicit operational recovery process is introduced.
11. Webhook/payment-status verification remains authoritative for marking a payment `Paid`; retry success only establishes a provider checkout order/session.

## Audit evidence

Each attempt retains `AttemptCount`, `LastAttemptAtUtc`, `NextRetryAtUtc`, `ProcessingStatus`, `LastErrorCode`, provider order ID and original idempotency key. The original payment transaction is the audit anchor for all recovery attempts.

## Accounting boundary

Retry processing changes payment-provider operational state only. It does not recalculate subscription prices, discounts, platform fees, taxes, commissions or settlement amounts.
